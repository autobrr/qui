# Triage playbook

How to triage one discussion in the Issue Triage or Feature Requests categories. The triage workflow (`.github/workflows/triage.yml`) and the local `/triage` skill both obey this file.

## Labels

A triaged discussion carries one category label and one state label.

- Category: `bug`, `enhancement`.
- State: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`.

`needs-triage` moves to one of the other four states. `needs-info` moves back to `needs-triage` when the reporter replies. When you add a state label, remove the old one.

Extra labels with a role in triage:

| Label | Meaning |
| --- | --- |
| `needs-confirmation` | The discussion template adds it to every bug report. Remove it when the code path confirms the report. |
| `maybe-later` | A request that a human must judge on scope. Pairs with `ready-for-human`. |
| `qbit-native-feature` | A control that the qBittorrent WebAPI exposes and qui lacks. Always an accepted enhancement. |
| `external-bug` | The bug is in another program. Closed as `wontfix`. |

Area labels (`cross-seed`, `web`, `backend`, and more) are extra. Add the ones that fit.

## Writes

In the workflow, `./.github/scripts/discussion-write.sh` is the only write path. It acts on the discussion under triage. The operations are `add-label`, `remove-label`, `comment`, `close`, and `create-issue`. The workflow caps the number of calls, so pass every label name in one `add-label` call and one `remove-label` call.

Start every comment with this line:

```
> *This was generated by AI during triage.*
```

Only a local session writes `.out-of-scope/`, when a human rejects a request on scope.

## Steps

1. Read the discussion, its comments, and its labels. If a comment holds prior triage notes, read them first. Do not ask a question that those notes already answer.
2. Read `CONTEXT.md` and `docs/architecture.md` for the area that the discussion names.
3. Search for the same request in open and closed discussions and in open issues. Search by the domain concept, not by the words of the reporter.
4. Read every file in `.out-of-scope/`. Compare by concept, not by keyword.
5. For a bug, find the code path. Decide whether the report agrees with the code. For an enhancement, search the codebase for an existing implementation.
6. Pick one outcome from the list that follows. If two outcomes fit, pick `needs-info`.
7. Apply the outcome with the write operations named for it.

## Outcomes

### Mechanical wontfix

Close a discussion only for one of these reasons:

| Reason | Close reason | Comment content |
| --- | --- | --- |
| Duplicate of an open discussion or issue | `DUPLICATE` | Link to the original. |
| Already implemented | `RESOLVED` | Where the feature lives and how to use it. |
| Matches a concept in `.out-of-scope/` | `RESOLVED` | The reason from the file and a link to it. |
| Bug in another program | `RESOLVED` | Name the program. Add the `external-bug` label. |

Apply it: add `wontfix`, remove the old state label, post the comment, then `close <reason>`.

Every other rejection is a human decision. For a request that looks out of scope, add `ready-for-human` and `maybe-later`, remove `needs-triage`, and post no comment.

### qBittorrent parity

qui mirrors the qBittorrent WebAPI. A request for a control that qBittorrent exposes and qui lacks is always an accepted `enhancement`. Add `qbit-native-feature`. Never close it as `wontfix`. The brief names the WebAPI endpoint.

### needs-info

The report lacks a detail that blocks a decision. Post this comment, add `needs-info`, remove `needs-triage`:

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**What we have established so far:**

- point 1

**What we still need from you (@reporter):**

- question 1
```

Each question must name the exact detail you need. Put everything you established into the first list, so the next pass does not repeat your work.

### ready-for-agent

The request is fully specified and an agent can build it without a design decision. The issue becomes the only open thread for the work:

1. Run `create-issue` with a short title and the agent brief as the body. The command prints the issue URL.
2. Post one comment: the disclaimer line, then `Tracked in <issue URL>.`
3. Add `ready-for-agent`, remove `needs-triage`.
4. Run `close RESOLVED`.

Do not post the brief on the discussion. It lives in the issue, and the issue body links back with `From discussion #N`.

### ready-for-human

The request needs a decision that only a human can make: UI placement, product scope, external access, or manual testing. Post the agent brief with one extra line, `**Why a human:**`, that names the decision. Add `ready-for-human`, remove `needs-triage`. Do not create an issue.

## Agent brief

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug / enhancement
**Summary:** one line

**Current behavior:**
What happens now. For a bug, the broken behavior. For an enhancement, the status quo.

**Desired behavior:**
What happens after the work is complete. Name edge cases and error conditions.

**Key interfaces:**
- `TypeName`: what changes and why
- `functionName()`: what it returns now and what it must return

**Acceptance criteria:**
- [ ] One testable criterion per line

**Out of scope:**
- What this work must not change
```

Brief rules:

- Describe behavior, not procedure. The agent explores the code itself.
- Name types, functions, endpoints, and config keys. Do not name file paths or line numbers. They go stale.
- Each acceptance criterion is testable on its own.

## Privacy

Never repeat a tracker URL that has a path, query, or key. Never repeat a release name copied from the report. Describe the shape instead: "an anime season pack with a bracketed group tag".
