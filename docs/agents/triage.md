# Triage playbook

How to triage one discussion in the Issue Triage or Feature Requests categories. The triage workflow (`.github/workflows/triage.yml`) and the local `/triage` skill both obey this file. The workflow triages only the Issue Triage category. A maintainer triages feature requests with `/triage`.

## Labels

A triaged discussion carries one category label and one state label.

- Category: `bug`, `enhancement`.
- State: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`.

`needs-triage` moves to one of the other four states. `needs-info` moves back to `needs-triage` when a comment supplies the missing information. When you add a state label, remove the old one.

Extra labels with a role in triage:

| Label | Meaning |
| --- | --- |
| `needs-confirmation` | The discussion template adds it to every bug report. Remove it when the code path confirms the report. |
| `maybe-later` | A request that a human must judge on scope. Pairs with `ready-for-human`. |
| `qbit-native-feature` | A control that the qBittorrent WebAPI exposes and qui lacks. Always an accepted enhancement. |
| `external-bug` | The bug is in another program. Closed as `wontfix`. |
| `pending-close` | Triage found a likely duplicate. If nobody comments for 1 day, the daily sweep closes the discussion as a duplicate. Until then, it takes the place of the state label. |

Area labels (`cross-seed`, `web`, `backend`, and more) are extra. Add the ones that fit.

## Writes

In the workflow, `./.github/scripts/discussion-write.sh` is the only write path. It acts on the discussion under triage. The operations are `add-label`, `remove-label`, `comment`, `close`, and `create-issue`. The workflow caps the number of calls, so pass every label name in one `add-label` call and one `remove-label` call.

Start every comment with this line:

```
> *This was generated by AI during triage.*
```

End every comment with a hidden marker on its own line. The marker names the outcome:

```
<!-- qui-triage:<outcome> -->
```

The outcomes are `needs-info`, `pending-duplicate`, `duplicate`, `already-implemented`, `already-fixed`, `out-of-scope`, `external-bug`, `ready-for-agent`, `ready-for-human`, and `log-handoff`. The daily sweep writes `duplicate` and `stale` in the comments that it posts. When a triage run stops at its $5 budget before it applies an outcome, the workflow adds `ready-for-human` and posts a comment that ends with `budget-stop`.

Only a local session writes `.out-of-scope/`, when a human rejects a request on scope.

## Steps

1. Read the discussion, its comments, and its labels. If the discussion is closed, stop and report that it was triaged before. If it carries `needs-info`, `pending-close`, `ready-for-agent`, `ready-for-human`, or `wontfix`, and no human has commented after the last triage comment, stop and report the same. The exception is a local session on a `ready-for-human` discussion whose last triage comment is a log hand-off: continue, and fetch the logs. If it carries `pending-close` and the reporter commented after the last triage comment, follow "Reply to a likely duplicate". If humans commented but the comments do not add the information that triage asked for, stop without a write and report that the information is still missing. If the missing information is in logs behind a log link, use the log hand-off in `ready-for-human` instead. If a comment holds prior triage notes, read them first. Do not ask a question that those notes already answer. Collect every log link from the Log link field, the description, and the comments. In a local session, fetch the logs as `docs/agents/issue-tracker.md` describes. The workflow cannot fetch them.
2. Read `GLOSSARY.md`, `docs/architecture.md`, and the ADRs in `docs/adr/` for the area that the discussion names.
3. Search for the same request in open and closed discussions and in open issues. Search by the domain concept, not by the words of the reporter.
4. Read every file in `.out-of-scope/`. Compare by concept, not by keyword.
5. For an enhancement, search the codebase for an existing implementation. For a bug, find the code path and decide whether the report still agrees with the code. If it does not, search merged pull requests in that area with `gh search prs --repo <owner/repo> --merged` for the fix. The current release is `gh release list --limit 1 --exclude-pre-releases`.
6. Pick one outcome from the list that follows. If two outcomes fit, pick `needs-info`.
7. Apply the outcome with the write operations named for it.

## Outcomes

### Mechanical wontfix

Close a discussion at once only for one of these reasons. A duplicate stays open for 1 day. See "Likely duplicate".

| Reason | Close reason | Comment content |
| --- | --- | --- |
| Already implemented | `RESOLVED` | Where the feature lives and how to use it. |
| Bug already fixed | `RESOLVED` | The release or pull request that fixed it. |
| Matches a concept in `.out-of-scope/` | `RESOLVED` | The reason from the file and a link to it. |
| Bug in another program | `RESOLVED` | Name the program. Add the `external-bug` label. |

Apply it: add `wontfix` (not for a fixed bug), remove the old state label, post the comment, then `close <reason>`.

Every other rejection is a human decision. For a request that looks out of scope, add `ready-for-human` and `maybe-later`, remove `needs-triage`, and post no comment.

### Likely duplicate

The discussion asks for the same thing as an open discussion or issue. Post this comment, add `pending-close`, remove the old state label:

```markdown
> *This was generated by AI during triage.*

This looks like a duplicate of #N: one sentence on the shared problem or request.

Possible duplicates, most likely first:

- #N: what it covers and why it matches.
- #M: what it covers and how it differs.

Please add a 👍 or your details to #N. If nobody comments here for 1 day, this discussion closes as a duplicate. If your report is different, reply and say how.

<!-- qui-triage:pending-duplicate -->
```

List one to four candidates. Leave out a candidate that you would not link to the reporter. If no candidate is a clear match, pick another outcome.

#### Reply to a likely duplicate

The reporter commented on a `pending-close` discussion. Read the comment and do one of these:

- If the reporter says how the report differs, remove `pending-close` and add `needs-triage`. Then continue with step 2, and use the difference that the reporter gave.
- If the reporter agrees that it is a duplicate, add `wontfix` and remove `pending-close`. Post a comment that links the original and ends with `<!-- qui-triage:duplicate -->`. Then `close DUPLICATE`.
- In all other cases, write nothing. The daily sweep closes the discussion 1 day after the comment.

### qBittorrent parity

qui mirrors the qBittorrent WebAPI. A request for a control that qBittorrent exposes and qui lacks is always an accepted `enhancement`. Add `qbit-native-feature`. Never close it as `wontfix`. It goes to `ready-for-human` like every `enhancement`, and the brief names the WebAPI endpoint.

### needs-info

The report lacks a detail that blocks a decision. Post this comment, add `needs-info`, remove `needs-triage`:

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**What we have established so far:**

- point 1

**What we still need from you (@reporter):**

- question 1
```

If logs would help, ask the reporter to upload them at https://bin.getqui.com and post the Paste link in a comment.

Each question must name the exact detail you need. Put everything you established into the first list, so the next pass does not repeat your work.

A bug report whose code path no longer matches the report, with no fix found in merged pull requests, is also `needs-info`: ask the reporter to retest on the current release and name that release. A report that still matches the code is a confirmed bug and goes to `ready-for-agent` or `ready-for-human`. The daily sweep closes a `needs-info` discussion if nobody answers in 30 days.

### ready-for-agent

`bug` only. An `enhancement` never becomes an issue in triage, whatever category it was filed in: which requests get built is a human decision. An `enhancement` that is not `needs-info` or a mechanical wontfix goes to `ready-for-human`.

The bug is confirmed against the code path and an agent can fix it without a human decision. Do the design check first. If the check finds a design question, the bug goes to `ready-for-human`.

#### Design check

The fix has a design question if one of these is true:

- The fix goes against an ADR, or it needs a new decision that an ADR would record.
- The fix needs a domain term that `GLOSSARY.md` does not define, or it uses a glossary term with a different meaning.
- The same fault can happen through more than one caller, and no module owns the broken behavior. The fix then adds the same guard in each caller, or it needs a new shared module.
- The fix moves behavior from one module to another.
- The bug comes from state flags that can contradict each other, or from an event that is handled in a state where it is not allowed, and the fix adds one more flag or guard. Ask whether the state belongs in a pure reducer or a state machine.

In a local session, settle the design question with the maintainer. Write the decision into the agent brief, and record each new term or decision with the `domain-modeling` skill. Then continue with `ready-for-agent`.

Create the issue with `ready-for-agent`, as "Issue for a confirmed bug" describes.

### ready-for-human

A confirmed `bug` lands here when it needs a decision that only a human can make: UI placement, product scope, external access, manual testing, or a design question from the design check. The agent brief gets one extra line, `**Why a human:**`, that names the decision. For a design question, the line starts with `Design:` and asks the question, so the maintainer can run `/grill-with-docs` on it. Create the issue with `ready-for-human`, as "Issue for a confirmed bug" describes.

Every `enhancement` lands here too, and it stays a discussion. Post the agent brief with the `**Why a human:**` line as a comment. For an `enhancement` with no narrower decision, the line reads `Feature scope is a maintainer call.` A discussion that got `maybe-later` gets no comment. Add `ready-for-human` and remove `needs-triage`. Do not create an issue.

#### Log hand-off

Decide from the code first. A log link alone does not change the outcome. If the outcome depends on what the logs show, and the workflow cannot read them, hand the discussion to a maintainer:

1. Post one comment in the Triage Notes layout. List what triage established. In place of the questions for the reporter, name the question that the logs must answer. End with `@s0up4200 will read the logs that you shared. You do not need to do anything else.`
2. Add `ready-for-human`. Remove `needs-info` or `needs-triage`.

Do not post the agent brief. The maintainer fetches the logs, answers the question, and triages the discussion again.

In the local session that reads the logs, prove the cause with a live run before a comment names it. If the `field-test` skill is installed, use it. For a search bug, run the same search again with the cache skipped. If a live run is not possible, call the cause a theory in the comment, and name the check that can prove it.

### Issue for a confirmed bug

Every confirmed `bug` becomes an issue, in `ready-for-agent` or in `ready-for-human`. The issue becomes the only open thread for the work:

1. Run `create-issue <state> <title> <brief>`, where `<state>` is `ready-for-agent` or `ready-for-human`. The command labels the issue with the state and prints the issue URL.
2. Post one comment: the disclaimer line, then `Tracked in <issue URL>.`
3. Add the same state label to the discussion. Remove `needs-triage` and `needs-confirmation`.
4. Run `close RESOLVED`.

Do not post the brief on the discussion. It lives in the issue, and the issue body links back with `From discussion #N`.

## Agent brief

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug / enhancement
**Summary:** one line

**Current behavior:**
What happens now. For a bug, the broken behavior. For an enhancement, the status quo.

**Desired behavior:**
What happens after the work is complete. Name edge cases and error conditions.

**Key interfaces:**
- `TypeName`: what changes and why
- `functionName()`: what it returns now and what it must return

**Acceptance criteria:**
- [ ] One testable criterion per line

**Out of scope:**
- What this work must not change

**Domain:**
- Glossary terms: each `GLOSSARY.md` term that the brief uses. Name a missing term as a gap.
- ADRs: each ADR that the fix touches, or `None`.
- Owner: the module that owns the broken or missing behavior, or `None` when no module owns it. A missing owner is a design question.

**Logs:**
- Each log link from the report, exactly as the reporter wrote it, or `None`
```

Brief rules:

- Describe behavior, not procedure. The agent explores the code itself.
- Name types, functions, endpoints, and config keys. Do not name file paths or line numbers. They go stale.
- Put the fix in the module that owns the behavior, so that every caller gets it. Do not suggest a guard in one caller.
- Each acceptance criterion is testable on its own.
- Copy log links into **Logs** without a change, also links to other paste sites.

## Privacy

Never repeat a tracker URL that has a path, query, or key. A Paste link on bin.getqui.com is not a tracker URL. Only maintainers can read it, so copy it into the brief. Never quote log lines in a public comment or issue. Summarize them. Never repeat a release name copied from the report. Describe the shape instead: "an anime season pack with a bracketed group tag".
