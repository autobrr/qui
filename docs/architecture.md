# Architecture Notes

Internal reference for agents and maintainers. Read this before changing cross-module data flow, service boundaries, API routing, or long-lived architecture. For user-facing docs, use `documentation/docs/`.

## Module Map

- `cmd/qui/main.go`: CLI entrypoint for serve, config generation, user creation, and other commands. A new service is built in `serve` there (a consumer of sync events joins with `clientPool.AddSyncEventSink`), goes into `api.Dependencies` in `internal/api/server.go`, and `Server.Handler` registers its routes. `ClientPool.SyncedSpeeds` gives the speeds of each instance from its last sync, with no request to qBittorrent.
- `internal/api/`: HTTP handlers, middleware, and routing.
- `internal/qbittorrent/`: qBittorrent client pool and sync manager. It also owns the folder cleanup worker, which removes, through the `fsops` backends, the leftover folders after qui's deletes and moves, and gets orphan scan's ignore matcher through an interface.
- `internal/services/`: domain services such as cross-seed, Jackett/Torznab, reannounce, and tracker rules.
- `internal/services/automations/`: Automation rules. `run_plan.go` builds the Run plan of each run, and `service.go` carries out its Actions. Export to Instance is `executeExportToInstance` in `service.go`; `exportsAfterMoves` holds back an export whose save path uses `CurrentSavePath` while its torrent moves or has a move planned in the same run.
- `internal/fsops/`: filesystem backend abstraction. Service callsites moved from direct `os.*` calls to an `fsops.Backend` (migration in #1915) resolved per instance via `fsops.Pool`. Some direct `os.*` calls remain under `internal/services`, for example in `crossseed/partial_pool.go` and `trackericons`. The pool returns the local backend for instances with local filesystem access, returns the SFTP-backed remote backend (`internal/fsops/remote`; implements writes over sftp and advertises Write since #2942, reflinks unsupported) for an instance with SSH credentials and a confirmed host-key pin, and returns a noop backend otherwise (every filesystem op fails with `ErrNoFilesystemAccess`, or with the context error). The remote backend slots in at the pool (design: `docs/remote-backend-design.md`).
- `internal/sshpool/`: SSH connections for remote instances. One-shot dials with the stored key, host-key pinning against the confirmed pin and the read-only capability probe serve `ssh-test`; `Pool` keeps one persistent SSH+SFTP connection per instance for the remote backend, and up to three extra SFTP-only connections for a caller that copies on several, with keepalive, reconnect backoff, and an in-memory refusal memo for a mismatched or unreadable pin that a changed pin or a restart clears; after a restart, the next dial refuses an unchanged wrong key again.
- `internal/proxy/`: reverse proxy support for external apps.
- `internal/services/activity/`: in-process publish and subscribe for server activity. A service publishes a kind and IDs, never data. `/api/stream` sends each event to the browser as an `activity` event, and the frontend invalidates the matching react-query key prefix (`web/src/lib/activity-invalidation.ts`). The hub drops events while no stream is open, so after a reconnect the frontend invalidates every activity feed. The files, peers, and pieces of one torrent stay on polling, because qBittorrent does not push them. The file list comes from a database cache that can be up to five minutes old. The files endpoint skips the cache when the request has `refresh=1`.
- `internal/backups/`: scheduled snapshots.
- `internal/database/`: SQLite/Postgres migrations and database setup. A store that needs different SQL on Postgres branches on `dbinterface.DialectOf(db) == "postgres"` (`internal/dbinterface/querier.go`).
- `internal/models/`: data models and their SQL stores, in one or more files for each area. For example, `CrossSeedStore` is in `crossseed.go`, and its partial pool is in `crossseed_partial_pool.go`.
- `pkg/`: shared utilities.
- `web/src/`: frontend. Its stack and rules are in `web/AGENTS.md`.

## Core Data Flow

1. `SyncManager` fetches maindata from qBittorrent only when something asks for it. While a browser has an SSE stream open for an instance, a loop syncs that instance about every 2 seconds, and backs off to at most 30 seconds after errors. At other times, a read through a getter without `Unchecked` in its name syncs when the cache is more than 2 seconds old. A refresh hint after a write starts a sync 200 ms after the last hint, and at most 1 second after the first. A torrent that a client adds through the Client Proxy schedules a sync 200 ms later, but no sooner than 2 seconds after the start of the last sync of the instance. Adds that come before the scheduled sync starts share it. A sync that starts for another reason 200 ms or more after the add takes its place, and an earlier one does not. The tracker health loop reads each connected instance every 60 seconds, so with no browser open, the cache of a reachable instance is at most about 60 seconds old. `ReadInstanceTorrents` (the Copy groups job) starts no sync while the last attempt is at most 120 seconds old, unless qui wrote to the instance in the last 60 seconds, a torrent is moving, or the instance is down or never synced.
   - When the cache is stale, a getter without `Unchecked` in its name starts a sync in the background and returns the stale data at once. It waits for the sync only when the cache has no data yet, and for at most one request timeout (`refreshForRead` in `internal/qbittorrent/syncowner`). So the read after a write can return the state from before the write. Such a getter starts no sync while the sync after a proxied add is due. `Owner` starts each sync, so `PendingSync` knows whether a sync runs or is due soon. With `heldTitles` on, a webhook check that finds no match, and a season pack check that finds too few episodes, wait for a sync that runs or is due within 1 second, then look again. Each check waits once, for at most 1.5 seconds, so it can still answer "no match" when that sync takes longer or fails. A path that must start no sync uses the `Unchecked` getters (see `mainDataModeForRequest` in `internal/qbittorrent/maindata.go`).
   - go-qbittorrent calls `OnSyncUpdate` and `OnError` inside the singleflight call of the sync. If a callback calls `Sync`, the call joins the sync that runs the callback, and it waits until its context ends. Run such work on a new goroutine. A getter without `Unchecked` does not wait in a callback, because the cache has data by then.
2. After each sync that it applied, the sync manager publishes a Sync snapshot: the torrents of the instance as that sync left them. A sync that changed some torrents makes new objects only for those torrents, and the snapshot shares the other objects with the last one. Readers share the snapshot and never change a torrent of it (ADR 0051). `syncowner.Owner` holds the sync object of go-qbittorrent, and no other package holds it. A lint rule rejects code outside that package that names the sync type of the library, calls a method of it, or calls its constructors.
   - After a sync that changed the data, `Client.handleSyncUpdate` gets the Sync snapshot and the list of changes: the changed hashes, the removed hashes, and the hashes that the sync left out. It updates the completion and added hooks from the changed hashes only, then passes the same update to each `SyncEventSink`: the live-update stream, the Copy groups job, and the Transfer history adapter. No consumer gets a copy of the library, except the Transfer history adapter: while recording is on, at most once each 50 seconds for each instance, it copies the values that it records from each torrent (ADR 0052).
   - Before the delete path of the sync manager (`DeleteTorrents`) or the Client Proxy sends a delete to qBittorrent, it gives the `DeleteNoter` a delete note: the hashes and who deletes them. The Transfer history adapter is the `DeleteNoter`. The module keeps the note in memory until a reading shows that the torrent is gone, and stores its cause with the delete event. A delete with no note has the cause "outside qui".
3. Frontend reads state through REST APIs and receives live updates through SSE.
4. Cross-seed services react to torrent completion and search/match events.
